# Feasibility study — 16 October 2026

## Decision and achievable reliability

Build a single-process Python library and a small authenticated OpenAI-compatible chat gateway. Use LiteLLM 1.98.0 for provider translation and normalized responses/errors. Keep a custom admission/policy scheduler because account ownership groups, free-use evidence, heterogeneous capability constraints and one end-to-end deadline must be enforced together. Do not layer LiteLLM Router retries underneath scheduler retries.

This is practical for intermittent development and experiments. It is not an availability guarantee for five simultaneously busy coding agents. Long contexts consume token quotas rapidly; tool loops multiply requests; research prompts may need capabilities absent from the remaining free pool. Account keys can share organization/project limits. Separate accounts must be legitimate and their use must comply with each provider's policies; the software must not be used to evade restrictions. When all eligible targets are unavailable, wait on release/cooldown until the request deadline, then return a sanitized 504; immediate eligibility failures return 503 and admission overflow returns 429. No paid emergency fallback exists.

## Alternatives

1. **Selected:** LiteLLM SDK plus a local policy scheduler and FastAPI adapter. Small deployment, explicit free-only gate, one retry owner, simple agent-facing Python contract.
2. LiteLLM Router/Proxy alone: substantial supported load balancing, cooldown, retry and gateway functionality. Strong choice once deployment pools are homogeneous and centrally operated, but it does not establish free eligibility, trustworthy shared quota ownership, or dynamically validate this catalog. Adding those checks would still require policy integration. A direct Router plus a second independent scheduler introduces ambiguous retry and reservation ownership.
3. Distributed gateway with PostgreSQL and Redis: supports persistent spend, virtual keys and coordination across processes, but adds operational cost and failure modes without a current multi-host requirement. Defer until demand justifies it.

[LiteLLM routing](https://docs.litellm.ai/docs/routing) documents routing strategies, fallback and cooldown policies. The [minimal proxy deployment](https://docs.litellm.ai/docs/proxy/docker_quick_start) distinguishes plain gateway operation from database-dependent virtual keys and spend features. This implementation deliberately uses the SDK rather than claiming to run LiteLLM Proxy.

Free API access, finite promotional/trial credits, paid metered API access and consumer subscriptions are different products. This system admits no credit-funded or subscription-backed path. For providers without explicit zero-price routing, a documented model policy **and** an operator attestation that the account cannot bill are required. Those attestations cannot be proved automatically by the APIs used here. Default policy is empty; OpenRouter zero-priced variants are the only automatically admitted family. This conservative default leaves other configured accounts disabled for inference, not discarded.

## Feature assessment

| Feature | Purpose and LiteLLM support | Dependencies / free-tier practicality / limitations | Decision |
|---|---|---|---|
| Unified API | SDK translates providers to OpenAI-style chat. | LiteLLM; provider semantics differ and unsupported parameters must never be silently dropped. | Implement Python `chat()` and `/v1/chat/completions`. |
| Multiple capabilities | SDK has chat, embeddings and image APIs where adapters support them. | Each operation needs separate eligibility, context/dimension and price evidence; images often cost money. Embedding fallback cannot silently change vector dimensions or semantic space. | Chat now; embeddings/images deferred with an explicit extension design. |
| Smart routing | Router offers latency/usage/cost strategies. | Free-policy and capability evidence must precede selection; no reliable universal quality ranking or quota oracle. | Local filtering, fair account usage, deployment usage and observed latency now; learned quality routing deferred. |
| Load balancing | Router supports shuffled, least-busy and other strategies. | One process needs no Redis; unknown quotas require conservative concurrency. Key count cannot multiply group capacity. | Fair account/deployment reservations from first request; no sequential account exhaustion. |
| Automatic fallback | Router supports fallback groups and context fallback. | Must preserve capabilities and context; not every error is retryable. | Explicit same-contract fallback now, maximum three attempts including retries. |
| Retries and cooldowns | SDK/Router support retries and cooldown policies. | Retrying in several layers amplifies traffic. Retry-After is a lower bound; jitter must not shorten it. | Scheduler owns bounded retries, scoped cooldown and deadline; SDK retries disabled. |
| API gateway | LiteLLM Proxy supplies an OpenAI-compatible gateway. | Full proxy is an alternative, not another required hop. Small local gateway has fewer operational dependencies. | FastAPI chat subset now; full Proxy optional migration. |
| Virtual API keys | Proxy supports virtual keys. | Database-backed management, lifecycle and tenant ownership are unnecessary for one trusted local orchestrator. | Defer; one strong local bearer key now. |
| Rate limits and budgets | Proxy offers key/team/model limits and budgets. | Actual free quotas often unknown and shared. Dollar budgets are not a zero-spend guarantee. Persistent distributed budgets require infrastructure. | Bounded admission, group concurrency and reactive header/reset cooldown now; arbitrary paid budgets deferred. |
| Cost tracking | LiteLLM estimates costs from model prices; proxy can persist spend. | List-price estimates differ from free allowances and invoiced spend. Unknown must remain unknown. | Usage and provider-reported cost retained; no claim of audited billing. Persistent spend optional. |
| Logging and monitoring | LiteLLM callbacks and external integrations exist. | Content logging is inappropriate by default; integrations add services and may transmit prompts. | Safe in-memory counters, EWMA latency, status and attempt metadata now. External exporters optional. |
| Caching | SDK/proxy caching supports memory/Redis-backed responses. | Tool state, randomness, provider data policies and cache invalidation complicate coding workloads. Prompt content needs protected storage. | Off by default; optional future explicit opt-in with tenant/capability/model-aware keys and TTL. |
| Guardrails | LiteLLM supports guardrail integrations. | Many scanners cost money or add latency. Model routing is not a sandbox for executing generated code. | Request bounds, capability/free allowlists and JSON validation now. Content moderation, tool permission and code execution sandbox deferred to orchestrator scope. |
| Admin dashboard | Proxy provides administration UI. | Authentication, database and optional enterprise functions need separate evaluation. Unnecessary for initial library use. | Defer; authenticated JSON status now. |

## Limits that remain

No provider supplies a universally trustworthy model/access/free-balance/capacity snapshot. Discovery is metadata-only, performed at startup or explicit CLI invocation; no synthetic health polling occurs. Catalog evidence expires after 24 hours, so restart a long-running service to refresh it. Runtime cooldowns, counters and fairness are in memory and reset on restart. Do not restart to work around provider limits. Use a single service instance: multiple workers would multiply concurrency and lose coordinated state.

Output token caps do not prevent every provider's internal reasoning usage. Successful transport does not prove coding quality or correct tool arguments. JSON responses are parsed and schemas validated locally; tool execution belongs to future agents. Tool support and schema support are filtered independently, including their intersection. Provider changes can invalidate catalog metadata between refresh and request. Billing safety ultimately also requires correctly configured provider-side plans and spending controls.
